# API_AND_DATA.md

# Техническая спецификация данных и интеграций
## Проект: Telegram Mini App «Что посмотреть?»

## 1. Назначение

Документ фиксирует текущую модель данных, API и правила хранения состояния в MVP.

Главное архитектурное правило: общий каталог и пользовательская кинотека разделены.

## 2. Инфраструктура MVP

Frontend: Cloudflare Pages.

Backend: Cloudflare Pages Functions.

База: Cloudflare D1, binding `MOVIES_DB`.

Основные таблицы:

- `movies` — общий неперсональный каталог;
- `users` — пользователи;
- `user_movies` — связь пользователя с фильмом и личное состояние.

## 3. Таблица movies

Фактическая схема MVP:

```sql
CREATE TABLE IF NOT EXISTS movies (
  kinopoisk_id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  original_title TEXT,
  year INTEGER,
  type TEXT,
  countries_json TEXT,
  genres_json TEXT,
  description TEXT,
  short_description TEXT,
  duration_minutes INTEGER,
  rating_kp REAL,
  rating_imdb REAL,
  poster_url TEXT,
  backdrop_url TEXT,
  imdb_id TEXT,
  tmdb_id INTEGER,
  kp_url TEXT,
  trailer_url TEXT,
  source TEXT NOT NULL DEFAULT 'poiskkino',
  source_updated_at TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### Правила каталога

- `kinopoisk_id` — основной идентификатор записи MVP.
- Страны и жанры сейчас хранятся JSON-массивами.
- Неизвестный рейтинг хранится как `NULL`, не как `0`.
- Отсутствующий постер, описание или рейтинг не означает отсутствие фильма.
- `source` показывает происхождение/состояние записи:
  - `poiskkino` — полноценные данные поставщика;
  - `library_migration` — минимальная запись, ожидающая фонового обогащения;
  - `library_migration_failed` — запись с явной ошибкой конкретного фильма, исключённая из фоновой очереди, но доступная для повторной попытки при открытии карточки.

## 4. Внутренняя модель фильма frontend/API

Нормализованный объект включает:

```js
{

  title,
  originalTitle,
  year,
  type,
  genres: [],
  countries: [],
  desc,
  shortDescription,
  durationMinutes,
  time,
  posterUrl,
  backdropUrl,
  kp,
  imdb,
  imdbId,
  tmdbId,
  kpUrl,
  imdbUrl,

```

`countries` является обязательной частью внутренней модели для дальнейших фильтров по странам, эпохам и естественных запросов.

## 5. users

Таблица `users` поддерживает Telegram identity через `telegram_user_id`, а также имя, username и avatar URL.

Telegram-пользователь получает отдельный внутренний `id` формата `telegram:<telegram_user_id>`, а `telegram_user_id` используется как уникальная внешняя identity. `user_movies` привязывается к внутреннему `users.id`, а не напрямую к сырому Telegram ID.

Проверено в Production:

- `Telegram.WebApp.initData` успешно приходит из Mini App;
- сервер проверяет подпись и `auth_date`;
- пользователь создаётся/обновляется в `users`;
- личная кинотека читается по подтверждённому Telegram-пользователю;
- разные Telegram-пользователи получают разные `user_movies`;
- один Telegram-пользователь получает одну библиотеку на разных устройствах.

`local_test_user` не используется `/api/user-library` как текущий resolver. Он сохранён только как резервная копия старой миграции; решение о его окончательном удалении принимается отдельно.

## 6. user_movies

Пользовательское состояние хранится отдельно от `movies`.

Ключевые поля:

- `user_id`;
- `kinopoisk_id`;
- `status`;
- `for_tonight`;
- `personal_rating`;
- `watched_at`;
- `added_at`;
- `selected_for_tonight_at`;
- `note`;
- `created_at`;
- `updated_at`.

Составной первичный ключ:

`(user_id, kinopoisk_id)`

## 7. Пользовательские статусы

Допустимые сервером значения:

- `none`;
- `watchlist`;
- `watched`;
- `rewatch`.

Основная модель текущего интерфейса:

```js
{
  status: "watchlist" | "watched" | "none",
  forTonight: boolean,
  userRating,
  watchedDate
}
```

### Правила

- «На вечер» не является отдельным статусом.
- `for_tonight` — независимый флаг.
- При переводе фильма в `watched` `for_tonight` автоматически сбрасывается.
- Личная оценка — целое число от 1 до 10 или `NULL`.
- Фильм не считается просмотренным автоматически.

## 8. Серверная личная кинотека

Первичная серверная миграция создала 1098 `user_movies` для `local_test_user`.

На Telegram-этапе эти 1098 записей безопасно скопированы на подтверждённого владельца через одноразовый защищённый legacy-механизм. После успешных Production-проверок серверный `/api/legacy-library-claim` удалён. Исходные записи `local_test_user` пока сохранены как резерв и не участвуют в определении текущего пользователя.

Проверено в Production под Telegram identity:

- читаются все 1098 позиций основной библиотеки;
- включение «На вечер» записывается на сервер;
- после закрытия и повторного открытия Mini App «На вечер» остаётся сохранённым;
- данные `local_test_user` не подмешиваются Telegram-пользователям;
- второй Telegram-пользователь начал с отдельной пустой библиотеки и сохранил собственный фильм, не изменив библиотеку первого;
- библиотека основного Telegram-пользователя совпадает на разных устройствах.

Сервер — основной источник состояния.

`localStorage` остаётся:

- локальным cache/fallback;
- очередью повторной синхронизации при временной сетевой ошибке;
- хранит идентификатор последнего Telegram-пользователя для очистки пользовательского cache при смене аккаунта.

При смене Telegram user frontend удаляет локальные `movieAppImportedMoviesV1`, `movieAppStatesV1` и `movieAppPendingLibrarySyncV1`, чтобы исключить смешивание личных данных между аккаунтами.

В текущем frontend также временно сохраняется `movieAppServerLibraryMigratedV1`. Это больше не разрешение на server-side legacy claim: маркер используется существующим `index.html` как совместимость со старой localStorage → server миграцией и одновременно как условие синхронизации новых импортированных фильмов. Удалять его нужно отдельной правкой после отвязки от активного сценария импорта.

## 9. Исправление неизвестных рейтингов

Во время первой миграции часть неизвестных рейтингов была ошибочно сохранена как `0`.

Для `source = 'library_migration'` ошибочные `rating_kp = 0` были исправлены на `NULL`.

Правило на будущее:

```text
нет рейтинга → NULL
реальный рейтинг 0 → не использовать как замену отсутствующего значения
```

В «Мои фильмы» минимальный рейтинг **не применяется по умолчанию**.

## 10. Рабочие API

### GET /api/catalog-search

Поиск по общей базе D1.

Примеры:

```text
GET /api/catalog-search?q=Бес&limit=30
GET /api/catalog-search?preset=comedy
GET /api/catalog-search?preset=rating7
GET /api/catalog-search?preset=starter
```

Правила:

- текстовый поиск от 2 символов;
- поиск по `title` и `original_title`;
- лимит до 50;
- поддерживаются быстрые пресеты;
- `starter` выбирает сильные и более разнообразные позиции.

Текущие пресеты:

- `comedy`;
- `thriller`;
- `horror`;
- `rating7`;
- `short`;
- `new`;
- `starter`.

### POST /api/movie-details

Используется для полной карточки и серверного обогащения запрошенных фильмов.

Принцип:

1. прочитать запрошенные фильмы из D1;
2. полноценную запись `source='poiskkino'` считать cache hit;
3. отсутствующую запись, `source='library_migration'` или `source='library_migration_failed'` считать требующей обогащения;
4. запросить внешний источник только для таких ID;
5. нормализовать и сохранить полученные данные в `movies`;
6. если внешний API временно не сработал, вернуть имеющуюся минимальную запись, чтобы карточка не исчезала у пользователя.

Таким образом, минимальные миграционные записи постепенно улучшаются естественным образом при открытии карточек, а уже готовые записи не расходуют лимит поставщика повторно. `library_migration_failed` не участвует в фоновой очереди, но получает ещё одну попытку, когда пользователь действительно открывает эту карточку.

Кэш D1 был отдельно проверен на фильме `kinopoisk_id=712`: ответ возвращался из D1 с `cacheHit=true`.

### /api/user-library

Работает только с подтверждённой Telegram-сессией. Временный `resolveUserId() => local_test_user` удалён.

Если валидной серверной сессии нет, endpoint возвращает `401` и не выдаёт чужую библиотеку.

Поддерживает:

- чтение всей кинотеки;
- фильтрацию по статусу;
- выбор только `forTonight`;
- чтение одной записи по `kinopoiskId`;
- создание/обновление пользовательского состояния;
- bulk migration библиотеки.

При bulk migration неизвестный фильм может получить минимальную запись в `movies` с `source='library_migration'` без обязательного вызова внешнего API.

### POST /api/telegram-auth

Серверная проверка Telegram Mini App identity.

Запрос должен передавать сырую строку `Telegram.WebApp.initData` в заголовке:

```text
x-telegram-init-data: <raw initData>
```

Сервер:

1. получает `initData`;
2. строит Telegram data-check-string;
3. проверяет HMAC-SHA-256 подпись с использованием `TELEGRAM_BOT_TOKEN`;
4. проверяет `auth_date`, чтобы не принимать устаревшую сессию;
5. извлекает пользователя только после успешной проверки;
6. ищет `users.telegram_user_id`;
7. обновляет профиль существующего пользователя либо создаёт нового;
8. возвращает внутренний `userId` и подтверждённые публичные данные пользователя.

`initDataUnsafe` не используется как источник авторизации.

По умолчанию допустимый возраст `initData` — 24 часа. Его можно изменить через `TELEGRAM_AUTH_MAX_AGE_SECONDS`.

Для работы требуется server-side Secret:

- `TELEGRAM_BOT_TOKEN`.

`GET /api/telegram-auth` не поддерживается.

### POST /api/telegram-session

Создаёт пользовательскую серверную сессию после повторной серверной проверки Telegram `initData`.

Порядок:

1. `telegram-entry.html` получает `Telegram.WebApp.initData`;
2. отправляет его в `x-telegram-init-data` на `/api/telegram-session`;
3. endpoint использует тот же безопасный Telegram verifier;
4. после успешной проверки создаётся подписанный HMAC session token;
5. token записывается в cookie `wtw_session` с атрибутами `HttpOnly; Secure; SameSite=Lax`;
6. `/api/user-library` извлекает `userId` только из валидной подписанной session cookie.

По умолчанию срок сессии — 24 часа. При необходимости может быть изменён через `TELEGRAM_SESSION_TTL_SECONDS`.

Bot token во frontend не передаётся.

### POST /api/catalog-enrich

Служебный endpoint для контролируемого пакетного обогащения каталога.

Назначение: постепенно заменять минимальные `library_migration` записи полноценными данными поставщика без ручного открытия каждой карточки и без зависания очереди на проблемных ID.

Правила:

- доступ только при наличии заголовка `x-catalog-enrich-key` со значением секрета `CATALOG_ENRICH_KEY`;
- секрет хранится только в Cloudflare Environment Variables / Secrets;
- выбираются только записи `source='library_migration'`;
- размер одной порции — от 1 до 25, максимум 25;
- безопасный дефолт при отсутствующем/невалидном `limit` — 1;
- `limit` поддерживается через `?limit=N` и JSON body, query-параметр имеет приоритет;
- внешний поставщик вызывается с ограниченной конкурентностью;
- успешная запись меняет `source` на `poiskkino`;
- уже обогащённые записи повторно не выбираются;
- очередь сортируется по `updated_at`, затем по `kinopoisk_id`;
- временная/сетевая/5xx ошибка оставляет `source='library_migration'`, но обновляет `updated_at`, перемещая запись в конец очереди;
- `404/410/422` считаются явной ошибкой конкретной записи: она переводится в `library_migration_failed` и исключается из фоновых партий;
- `401/402/403/429` считаются глобальными ограничениями поставщика и останавливают текущую партию после уже начатой группы запросов;
- `library_migration_failed` может повторно обогащаться через `/api/movie-details` при открытии карточки;
- `GET` не поддерживается.

Основные поля ответа:

- `requested` — сколько ID было выбрано для партии;
- `attempted` — сколько реально отправлено поставщику;
- `enriched` — сколько успешно сохранено;
- `failed` — сколько запросов завершилось ошибкой;
- `skipped` — сколько выбранных ID не отправлено после досрочной остановки партии;
- `quarantined` — сколько записей переведено в `library_migration_failed`;
- `retryLater` — сколько ошибок оставлено для будущей повторной попытки;
- `pendingBefore` / `pendingAfter` — размер фоновой очереди до и после запуска;
- `quarantinedBefore` / `quarantinedAfter` — количество записей вне фоновой очереди из-за явной ошибки конкретного фильма;
- `stopped` / `stopReason` — была ли партия досрочно остановлена глобальной ошибкой поставщика.

Queue-safe успешный сценарий проверен на Preview: `requested=1`, `attempted=1`, `enriched=1`, `failed=0`, `stopped=false`.

Используемые server-side secrets/variables:

- `POISKKINO_API_TOKEN` — Secret;
- `CATALOG_ENRICH_KEY` — Secret;
- `TELEGRAM_BOT_TOKEN` — Secret.

Временная `LEGACY_LIBRARY_OWNER_USER_ID` больше не нужна рабочему коду после удаления server-side legacy claim. После merge cleanup её следует удалить из Cloudflare Environment отдельно; до merge Production всё ещё использует старую версию приложения.

### GitHub Actions: ежедневное обогащение

Workflow `.github/workflows/catalog-enrichment.yml` используется для фонового вызова Production endpoint.

Правила:

- scheduled-run запускается один раз в сутки;
- scheduled-run использует 6 партий по 25 фильмов — до 150 попыток в сутки;
- ручной `workflow_dispatch` по умолчанию безопасен: 1 партия × 1 фильм;
- для ручного запуска размер партии и количество партий увеличиваются только явным выбором;
- workflow передаёт `CATALOG_ENRICH_KEY` из GitHub Repository Secret и не хранит его в коде;
- при пустой очереди выполнение завершается досрочно;
- при `stopped=true` дальнейшие партии не запускаются;
- транспортный timeout `curl` с кодом 28 учитывается отдельно, после короткой паузы workflow продолжает следующую партию;
- другие ошибки `curl` завершают job;
- HTTP non-200 завершают job с диагностикой ответа;
- точное время старта cron не является частью продуктового контракта: GitHub Actions может запустить scheduled job позже указанной минуты.

Проверено в Production:

- ручной workflow-run: `attempted=1`, `enriched=1`, `failed=0`;
- первый самостоятельный scheduled-run: `attempted=150`, `enriched=150`, `failed=0`;
- scheduled-run #9: первая партия `attempted=25`, `enriched=24`, `failed=1`, `retryLater=1`, `pendingAfter=328`; вторая партия получила timeout 120 секунд, после чего workflow был усилен для продолжения следующих партий при коде `curl 28`.

### /api/import-kinopoisk

Импортирует публичный список Кинопоиска через серверный сценарий.

Логин/пароль пользователя Кинопоиска не хранятся.

## 11. Удалённый временный API

`functions/api/user-library-write-test.js` использовался только для проверки записи и удалён.

Одноразовый `functions/api/legacy-library-claim.js` использовался только для безопасного переноса старой библиотеки на подтверждённого Telegram-владельца и удалён после успешного Production-аудита.

Временная диагностическая страница `telegram-auth-check.html` также удалена после успешной проверки Telegram identity и не является частью рабочего продукта.

## 12. Источники метаданных

Текущий серверный источник обогащения — ПоискКино API.

Архитектурное правило: внешний поставщик сменяем.

Frontend не должен содержать его секреты и не должен зависеть от сырого формата ответа поставщика.

## 13. Состояние каталога после миграции

В `movies` присутствовали записи для 1098 позиций пользовательской кинотеки.

Историческая контрольная точка после queue-safe Preview-теста:

- 294 записи полноценно обогащены через внешний API;
- 804 записи оставались `library_migration`;
- неизвестные рейтинги миграционных записей после исправления представлены как `NULL`.

После включения ежедневного scheduled-run эта контрольная точка является исторической, а не текущим остатком очереди. Живое состояние следует определять по `pendingAfter` в последних запусках либо отдельным аудитом D1. Последняя подтверждённая Production-контрольная точка на момент этого документа — `pendingAfter=328`.

После включения queue-safe обработки часть явно недоступных записей может перейти в `library_migration_failed`; это не удаляет фильм и не меняет `user_movies`.

Каталог может постепенно обогащаться без изменения `user_movies` двумя путями:

1. по требованию при открытии карточки через `/api/movie-details`;
2. пакетно через защищённый `/api/catalog-enrich`, включая ежедневный GitHub Actions scheduled-run.

После завершения фоновой очереди проводится финальный аудит: остаток `library_migration`, количество `library_migration_failed`, полнота ключевых полей каталога и сохранность пользовательских связей `user_movies`. Этот аудит не блокирует Telegram-разработку.

## 14. Фильтры

Текущая пользовательская фильтрация поддерживает:

```js
{
  type,
  genres,
  minKinopoiskRating,
  yearFrom,
  yearTo,
  status
}
```

Правила:

- жанров может быть несколько;
- год задаётся пресетом или диапазоном;
- минимальный КП применяется только после явного выбора пользователя;
- пустые фильтры не должны скрывать фильмы с неизвестными значениями без понятной причины.

Будущие фильтры:

- страна;
- десятилетие;
- комбинации страны + жанра + эпохи.

## 15. Безопасность

- API-ключи только на сервере.
- Секреты через environment variables / secrets.
- `CLOUDFLARE_ACCOUNT_ID` может храниться как обычная переменная; токены и служебные ключи — как Secret.
- `CLOUDFLARE_BROWSER_TOKEN`, `POISKKINO_API_TOKEN`, `CATALOG_ENRICH_KEY` и `TELEGRAM_BOT_TOKEN` должны храниться как Secret.
- Frontend не считается доверенной средой.
- Telegram `initDataUnsafe` нельзя использовать как доказательство identity.
- Telegram `initData` проверяется сервером до использования Telegram user ID.
- После проверки Telegram identity пользовательские API работают через подписанную HttpOnly session cookie.
- Все пользовательские изменения проверяются на сервере.
- Пользователь имеет доступ только к собственным `user_movies`.
- `local_test_user` не используется как текущая identity и остаётся только резервной исторической копией.
- Внешним поставщикам каталога не передаются личные пользовательские данные.

## 16. Telegram — Production-этап закрыт

Реализовано и проверено в Production:

1. серверная проверка `initData`;
2. создание/обновление пользователя в `users`;
3. `telegram-entry.html` с Telegram Web App SDK;
4. серверная session cookie через `/api/telegram-session`;
5. `/api/user-library` работает с проверенной Telegram identity;
6. локальный cache очищается при смене Telegram-пользователя;
7. BotFather / Menu Button настроен на Production `/telegram-entry.html`;
8. 1098 старых записей безопасно скопированы владельцу;
9. проверена запись «На вечер» и сохранение после повторного открытия Mini App;
10. подтверждена независимость двух разных Telegram-пользователей;
11. подтверждена одна и та же библиотека одного Telegram-пользователя на втором устройстве;
12. одноразовый server-side legacy claim удалён.

Резервные записи `local_test_user` пока остаются в D1. Их судьба решается отдельно и не должна быть связана с рабочей авторизацией.

Frontend-маркер старой localStorage → server миграции пока остаётся до отдельной отвязки от синхронизации импорта. Это техническая совместимость frontend и не означает наличие server-side legacy claim.

## 17. Не входит в текущий MVP

- групповой выбор;
- Tinder/турнир;
- AI-подбор;
- сложные коллекции.

Эти сущности не должны усложнять текущие таблицы и API раньше времени.

## 18. Правила изменения схемы

Перед добавлением нового поля или сущности:

1. проверить, помогает ли это текущему MVP;
2. определить, относится поле к каталогу или пользователю;
3. обновить этот документ;
4. сделать воспроизводимую миграцию;
5. сохранить обратную совместимость frontend/API там, где это разумно.

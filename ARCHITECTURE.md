# ARCHITECTURE.md

# Архитектура приложения «Что посмотреть?»

## 1. Назначение

Документ фиксирует архитектуру текущего MVP и правила дальнейшего развития без полной переделки приложения.

Главная цель архитектуры — быстро развивать продукт, сохраняя независимость от конкретного поставщика данных, способа авторизации, облачной инфраструктуры и региона размещения.

## 2. Главный принцип

Приложение разделено на два контура:

1. общий каталог фильмов и сериалов;
2. пользовательские данные.

Эти контуры связаны идентификатором фильма, но не дублируют данные друг друга.

## 3. Контур каталога

Каталог содержит только неперсональные данные:

- название;
- оригинальное название;
- тип;
- год;
- жанры;
- страны;
- описание;
- длительность;
- постер;
- backdrop;
- внешние рейтинги;
- внешние идентификаторы;
- ссылки.

Текущая таблица: `movies` в Cloudflare D1.

Каталог не должен содержать:

- пользовательские статусы;
- личные оценки;
- даты просмотра;
- пользовательские заметки;
- Telegram identity;
- данные авторизации.

## 4. Контур пользовательских данных

Текущие таблицы:

- `users`;
- `user_movies`.

`user_movies` хранит только связь пользователя с фильмом и личное состояние:

```js
{
  user_id,
  kinopoisk_id,
  status,
  for_tonight,
  personal_rating,
  watched_at,
  added_at,
  selected_for_tonight_at,
  note
}
```

Полная карточка фильма в пользовательской записи не дублируется.

## 5. Временная identity MVP

Пока Telegram-авторизация не подключена, используется:

`local_test_user`

Это временная точка входа, а не отдельная архитектура.

После Telegram-интеграции должна меняться только логика определения пользователя и проверки авторизации, а не структура каталога или основная модель `user_movies`.

## 6. Сервер — основной источник пользовательского состояния

Личная кинотека уже перенесена на сервер.

Подтверждено 1098 записей в `user_movies` после миграции.

Основной источник истины — D1.

`localStorage` используется только как:

- cache;
- fallback при временной недоступности сети;
- очередь повторной синхронизации;
- источник одноразовой миграции старого локального состояния.

Нельзя возвращаться к архитектуре, где личная кинотека существует только в браузере.

## 7. Внутренняя модель фильма

Frontend работает с нормализованной моделью, а не с сырым ответом внешнего API.

Пример:

```js
{
  kinopoiskId,
  title,
  originalTitle,
  year,
  type,
  genres: [],
  countries: [],
  desc,
  durationMinutes,
  posterUrl,
  backdropUrl,
  kp,
  imdb,
  imdbId,
  tmdbId,
  kpUrl,
  imdbUrl,
  trailer
}
```

Поле `countries` сохраняется уже сейчас, даже если расширенные фильтры по странам появятся позже.

## 8. Сменяемые поставщики данных

Внешний источник всегда считается сменяемым адаптером.

Текущий путь:

```text
Frontend
  ↓
Pages Functions / наш API
  ↓
Нормализация
  ↓
D1 cache
  ↓ при необходимости
Внешний поставщик
```

Frontend не должен обращаться к поставщику напрямую и не должен знать его секретные ключи.

Смена поставщика не должна требовать переписывания пользовательского интерфейса.

## 9. D1 как инфраструктура MVP и переносимость

Cloudflare D1 используется сейчас, потому что позволяет быстро получить рабочий MVP.

Cloudflare — текущая инфраструктура, но не обязательная часть долгосрочной архитектуры. Проект должен сохранять возможность переноса на другой облачный сервис или собственный сервер без полной переделки frontend и пользовательской модели.

Для переносимости:

- API-контракты документируются;
- данные нормализуются;
- секреты находятся в environment variables;
- frontend обращается только к HTTPS API;
- каталог и пользовательские данные логически разделены;
- схема базы и миграции должны быть воспроизводимыми;
- внешние сервисы подключаются через адаптеры;
- пользовательские данные должны иметь стандартный путь экспорта и резервного копирования.

Не привязывать бизнес-логику к Cloudflare-специфичным возможностям там, где это не даёт существенной пользы MVP.

## 10. Pages Functions

Текущие рабочие функции:

- `functions/api/import-kinopoisk.js`;
- `functions/api/movie-details.js`;
- `functions/api/catalog-search.js`;
- `functions/api/user-library.js`;
- `functions/api/catalog-enrich.js`.

Временный `user-library-write-test.js` удалён.

## 11. Каталог и кэш

`movie-details` работает по принципу cache-first:

1. проверить D1;
2. вернуть сохранённые данные, если они подходят;
3. при необходимости получить/обогатить данные через внешний API;
4. сохранить нормализованный результат.

Это уменьшает внешние запросы и делает каталог устойчивее к лимитам поставщика.

`catalog-search` работает только по нашей базе D1.

`catalog-enrich` используется только для фонового обогащения минимальных записей. Он не меняет `user_movies` и не является пользовательским API.

Допускается публичное кеширование только неперсональных данных каталога. Пользовательские профили, кинотека, личные оценки, история просмотров и токены авторизации не должны попадать в публичный cache.

## 12. Минимальные записи миграции и очередь обогащения

При переносе личной библиотеки фильм может быть создан в `movies` с минимальным набором данных и `source='library_migration'`.

Это правильнее, чем блокировать миграцию из-за отсутствия полной карточки.

Позже запись может быть независимо обогащена.

Пользовательская связь в `user_movies` при этом не меняется.

Для фонового обогащения действуют дополнительные правила:

- `library_migration` — запись в автоматической очереди;
- успешное обогащение переводит её в `poiskkino`;
- временная ошибка оставляет запись в `library_migration`, но обновляет `updated_at`, поэтому она уходит в конец очереди и не блокирует другие фильмы;
- явная ошибка конкретного фильма (`404/410/422`) переводит запись в `library_migration_failed` и исключает из фоновой очереди;
- `library_migration_failed` остаётся видимым пользователю и может повторно обогащаться через `movie-details` при открытии карточки;
- глобальные ошибки поставщика (`401/402/403/429`) должны останавливать пакет, а не массово менять состояния фильмов.

Такой механизм не требует дополнительной таблицы retry-state в MVP и не создаёт зависания фоновой очереди на одном проблемном ID.

## 13. NULL и отсутствие данных

Неизвестное значение должно отличаться от реального нулевого значения.

Пример:

```text
rating_kp неизвестен → NULL
```

Нельзя преобразовывать отсутствующий рейтинг в `0`, потому что это ломает фильтрацию, сортировку и UX.

То же правило применяется к другим необязательным полям.

## 14. Модель статусов

Основной пользовательский сценарий:

```text
none → watchlist → watched
```

`for_tonight` существует отдельно.

При `watched` он сбрасывается.

Сервер поддерживает также `rewatch` как расширяемое состояние, но UI текущего MVP не должен усложняться только ради него.

## 15. Навигационное состояние

Карточка фильма должна знать экран-источник.

Состояние списка, которое важно сохранить при возврате:

- экран;
- поисковый запрос;
- фильтры;
- выбранная вкладка «Моих фильмов»;
- позиция прокрутки.

Это часть UX-архитектуры, а не декоративная деталь: пользователь не должен заново восстанавливать контекст выбора после просмотра карточки.

## 16. Telegram-авторизация — следующий этап

Целевая схема:

```text
Telegram Mini App
  ↓ initData
Frontend
  ↓
Backend
  ↓ серверная проверка подписи
users
  ↓
user_movies
```

Правила:

- frontend не считается доверенной средой;
- Telegram ID без проверки `initData` не считается авторизацией;
- доступ к `user_movies` проверяется по текущему подтверждённому пользователю;
- переход с `local_test_user` не должен затрагивать каталог `movies`.

## 17. Персональные данные и региональное хранение

Каталог и персональные данные должны оставаться разделёнными.

Внешним поставщикам каталога нельзя передавать:

- Telegram ID;
- имя пользователя;
- личную кинотеку;
- оценки;
- историю просмотров;
- состав групп;
- заметки.

Для пользователей из России production-архитектура персональных данных должна проектироваться с учётом требований законодательства РФ. Зафиксированный ранее целевой принцип сохраняется: персональный контур российских пользователей должен иметь возможность размещаться в российской инфраструктуре.

К персональному контуру относятся как минимум:

- профиль пользователя;
- Telegram identity;
- настройки;
- `user_movies`;
- личные оценки;
- история просмотров;
- пользовательские заметки;
- будущие группы и приглашения;
- резервные копии и журналы, содержащие идентификаторы пользователей.

Текущая единая Cloudflare-инфраструктура допустима как MVP-реализация до production-решения по региональному хранению. Перед публичным production-запуском этот вопрос должен быть отдельно проверен юридически и технически.

Архитектура должна позволять в будущем разделить региональные контуры, например:

```text
Россия → пользовательский API и база в РФ
Европа → пользовательский API и база в Европе
Азия → пользовательский API и база в Азии
```

При этом frontend, внутренняя модель фильма и основной API-контракт должны оставаться общими.

## 18. Безопасность

Обязательные правила:

- API-ключи и секреты только на сервере;
- HTTPS;
- валидация входных данных;
- проверка прав пользователя на сервере;
- отсутствие секретов в `index.html`;
- отсутствие персональных данных в публичном репозитории;
- внешние URL проверяются и нормализуются;
- резервные копии персональных данных должны быть защищены;
- нельзя считать client-side identity достаточной авторизацией.

## 19. Логи и аналитика

До production-запуска внешняя аналитика, crash reporting и session replay должны подключаться только после отдельной проверки того, какие данные они собирают и куда передают.

Особое внимание:

- IP-адресам;
- Telegram ID;
- username;
- внутренним user ID;
- cookies и device ID;
- содержимому API-логов.

Для MVP предпочтительны минимальные технические логи без лишних персональных данных.

## 20. Архитектурные запреты

Не допускается:

- прямой вызов внешнего каталога из frontend с открытым токеном;
- хранение пользовательских данных внутри массива/таблицы каталога фильмов;
- зависимость UI от сырого формата внешнего API;
- смешивание каталога и пользовательских данных в одной сущности;
- хранение секретов в `index.html`;
- передача персональных данных внешнему поставщику каталога;
- использование одного внешнего ID как единственной долгосрочной идентичности без возможности адаптации;
- возврат к хранению единственной копии пользовательской кинотеки только в браузере.

## 21. Масштабируемость

Архитектура должна позволять без полной переделки:

- тысячи и миллионы фильмов;
- сотни жанров и стран;
- новые внешние поставщики;
- Telegram и другие способы авторизации;
- семейные/дружеские группы;
- региональные контуры хранения;
- новые механики рекомендаций.

Но эти возможности не должны заранее усложнять MVP.

## 22. Что не строим сейчас

До проверки основной гипотезы не добавлять в основной контур:

- групповой выбор;
- Tinder/турнир;
- AI-рекомендации;
- сложную систему коллекций;
- расширенную аналитику.

## 23. Основные архитектурные принципы

1. Каталог фильмов не содержит пользовательских данных.
2. Пользовательские данные не смешиваются с каталогом.
3. Сервер является основным источником пользовательского состояния.
4. Внешние сервисы считаются сменяемыми.
5. Frontend работает только с нашей нормализованной моделью и API.
6. Секреты не передаются во frontend.
7. Архитектура должна поддерживать региональное размещение персональных данных без переписывания продукта.
8. Cloudflare D1 — инфраструктура MVP, а не обязательная долгосрочная зависимость.
9. MVP остаётся простым, но не создаёт архитектурных тупиков.
10. Существенные архитектурные изменения фиксируются в документации.

## 24. Правило архитектурных изменений

Перед существенным изменением проверить:

1. помогает ли оно пользователю быстрее выбрать фильм;
2. не смешивает ли каталог и пользовательские данные;
3. не создаёт ли временную архитектуру, которую придётся выбросить;
4. не ломает ли текущие API и мигрированные данные;
5. сохраняет ли переносимость и требования к персональным данным;
6. нужно ли одновременно обновить `PROJECT.md`, `ROADMAP.md`, `DESIGN_SYSTEM.md` или `API_AND_DATA.md`.

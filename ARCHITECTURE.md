# ARCHITECTURE.md

# Архитектура приложения «Что посмотреть?»

## 1. Назначение документа

Этот документ фиксирует ключевые архитектурные принципы проекта.

Главная задача архитектуры — позволить быстро развивать MVP, не привязывая приложение навсегда к конкретному:

- поставщику фильмов;
- хостингу;
- облачному сервису;
- базе данных;
- региону размещения;
- frontend-фреймворку;
- способу авторизации.

---

## 2. Главный принцип

Приложение состоит из двух независимых контуров:

1. каталог фильмов и сериалов;
2. пользовательские данные.

Они не должны смешиваться в одной модели и зависеть друг от друга сильнее, чем это необходимо.

---

# 3. Контур каталога

Каталог содержит только неперсональные данные о фильмах и сериалах.

Примеры данных:

- название;
- оригинальное название;
- тип;
- год выпуска;
- жанры;
- страны;
- описание;
- продолжительность;
- постер;
- фоновое изображение;
- рейтинги;
- внешние идентификаторы;
- ссылки на трейлеры и внешние сервисы.

Каталог не должен содержать:

- Telegram ID;
- имя пользователя;
- личные оценки;
- историю просмотров;
- пользовательские заметки;
- списки «Хочу посмотреть»;
- семейные группы;
- данные авторизации;
- IP-адреса;
- технические идентификаторы пользователей.

---

# 4. Контур пользовательских данных

Пользовательские данные хранятся отдельно от каталога.

Примеры:

- внутренний ID пользователя;
- Telegram ID;
- имя и username;
- настройки;
- тема оформления;
- фильм в списке «Хочу посмотреть»;
- фильм, выбранный на сегодня;
- просмотренные фильмы;
- личные оценки;
- дата просмотра;
- заметки;
- семейные и дружеские группы;
- приглашения;
- история пользовательских действий.

Пользовательская запись должна ссылаться на фильм только по внутреннему идентификатору приложения.

Пример:

```json
{
  "user_id": "user_123",
  "media_item_id": "media_456",
  "status": "watchlist",
  "personal_rating": null,
  "watched_at": null
}
```

Полная информация о фильме в этой записи не дублируется.

---

# 5. Внутренняя модель фильма

Приложение работает только с собственной внутренней моделью фильма.

Внешние API не должны определять структуру frontend-кода.

Пример внутренней модели:

```json
{
  "id": "media_456",
  "type": "film",
  "title": "Интерстеллар",
  "original_title": "Interstellar",
  "year": 2014,
  "genres": [
    "Фантастика",
    "Драма"
  ],
  "countries": [
    "США"
  ],
  "description": "string",
  "runtime_minutes": 169,
  "poster_url": "string|null",
  "backdrop_url": "string|null",
  "ratings": {
    "kinopoisk": 8.7,
    "imdb": 8.7,
    "tmdb": 8.4
  },
  "external_ids": {
    "tmdb": "157336",
    "imdb": "tt0816692",
    "kinopoisk": "258687"
  }
}
```

---

# 6. Сменяемые поставщики данных

Любой внешний сервис считается сменяемым поставщиком.

Примеры:

- TMDB;
- Кинопоиск;
- IMDb;
- сторонние API;
- собственная база фильмов;
- ручная редактура;
- будущие лицензированные источники.

Frontend не должен обращаться к ним напрямую.

Правильная схема:

```text
Frontend
   ↓
Наш API
   ↓
Нормализатор
   ↓
TMDB / другой сервис / собственная база
```

Если поставщик меняется, интерфейс и пользовательская логика не должны переписываться.

---

# 7. API приложения

Frontend обращается только к нашему API.

Примеры:

```text
GET /api/search?q=
GET /api/media/{id}
GET /api/library
POST /api/library
PATCH /api/library/{id}
DELETE /api/library/{id}
```

API должен возвращать только внутреннюю модель данных приложения.

Нельзя передавать frontend-у:

- секретные API-ключи;
- токены внешних сервисов;
- служебные данные инфраструктуры;
- прямой доступ к базе данных.

---

# 8. Независимость от инфраструктуры

Приложение не должно зависеть от одного хостинга.

Cloudflare используется как удобная инфраструктура для MVP, но не является обязательной частью продукта.

Проект должен сохранять возможность переноса на:

- российский VPS;
- Vercel;
- Netlify;
- Supabase;
- Firebase;
- Render;
- Railway;
- Selectel;
- Yandex Cloud;
- VK Cloud;
- Timeweb Cloud;
- другой облачный сервис;
- собственный сервер.

Для этого:

- frontend обращается к стандартному HTTPS API;
- бизнес-логика не хранится в Cloudflare-специфичном коде без необходимости;
- переменные окружения и секреты не встраиваются в frontend;
- структура базы описывается отдельно;
- миграции данных должны быть воспроизводимыми.

---

# 9. Персональные данные и российский контур

Для пользователей из России персональные данные должны обрабатываться с учётом требований законодательства РФ.

На первом production-этапе рекомендуется хранить персональные данные всех пользователей в российской инфраструктуре.

В российском контуре хранятся:

- профили;
- Telegram ID;
- настройки;
- списки фильмов;
- личные оценки;
- история просмотров;
- группы;
- приглашения;
- резервные копии;
- журналы, содержащие идентификаторы пользователей.

Внешним поставщикам каталога не передаются:

- Telegram ID;
- имя пользователя;
- его список фильмов;
- личные оценки;
- история просмотров;
- состав групп;
- пользовательские заметки.

Допустимый запрос к внешнему каталогу:

```json
{
  "query": "Интерстеллар"
}
```

Недопустимый запрос:

```json
{
  "telegram_user_id": "123456789",
  "query": "Интерстеллар",
  "personal_rating": 10
}
```

---

# 10. MVP для семьи и друзей

На первом этапе приложение используется ограниченным кругом людей:

- семья;
- друзья;
- пользователи из России;
- пользователи из Таиланда;
- пользователи из других стран.

Для MVP допустима единая серверная инфраструктура.

Рекомендуемая схема:

```text
Пользователь
    ↓
Frontend
    ↓
Наш API
    ├── Пользовательские данные → база в РФ
    └── Каталог фильмов → внешний поставщик
```

Это проще, чем создавать несколько региональных контуров на старте.

---

# 11. Международное масштабирование

После роста проекта архитектура должна позволить добавить региональные контуры:

```text
Россия → API и база в РФ
Европа → API и база в Европе
Азия → API и база в Азии
```

При этом:

- внутренняя модель фильма остаётся общей;
- frontend остаётся единым;
- API-контракт остаётся единым;
- пользовательские данные хранятся в назначенном регионе;
- общий каталог фильмов может кешироваться отдельно;
- персональные данные не смешиваются между регионами без необходимости.

---

# 12. Авторизация

На этапе Telegram Mini App:

- frontend получает Telegram initData;
- backend проверяет подпись;
- пользователь определяется только после серверной проверки;
- frontend не считается доверенной средой;
- Telegram ID не используется как единственный секрет;
- права доступа проверяются на сервере.

---

# 13. Хранение данных

Каталог и пользовательские данные должны храниться в разных таблицах или схемах.

Пример:

```text
media_items
media_external_ids
media_ratings
users
user_library
user_ratings
groups
group_members
invitations
```

Не хранить JSON-объект фильма целиком внутри пользовательской записи.

---

# 14. Обновление каталога

Данные фильма могут обновляться независимо от пользовательских записей.

Если изменились:

- рейтинг;
- описание;
- постер;
- жанры;
- внешние ссылки;

достаточно обновить запись фильма.

Списки пользователей при этом не переписываются.

---

# 15. Кеширование

Допускается кеширование неперсонального каталога:

- результатов поиска;
- карточек фильмов;
- жанров;
- постеров;
- фоновых изображений;
- внешних рейтингов.

Нельзя кешировать в публичном кеше:

- профили;
- списки пользователей;
- личные оценки;
- группы;
- приглашения;
- историю просмотров;
- токены авторизации.

---

# 16. Логи и аналитика

До production-запуска нельзя подключать внешнюю аналитику без отдельной проверки.

Особое внимание:

- IP-адресам;
- Telegram ID;
- username;
- внутренним user ID;
- cookies;
- device ID;
- crash-reporting;
- session replay;
- журналам API.

На этапе MVP предпочтительны:

- минимальные серверные логи;
- отсутствие персональных данных в логах;
- обезличенные технические события;
- хранение логов в том же регионе, что и персональные данные.

---

# 17. Безопасность

Обязательные правила:

- API-ключи хранятся только на сервере;
- секреты задаются через переменные окружения;
- все запросы идут по HTTPS;
- пользовательские входные данные валидируются;
- действия с библиотекой требуют авторизации;
- доступ к данным проверяется по user_id;
- резервные копии защищаются;
- персональные данные не попадают в публичный репозиторий;
- frontend не содержит секретов;
- внешние URL проверяются и нормализуются.

---

# 18. Переносимость

Для упрощения переноса проекта:

- API-контракты документируются;
- схема базы хранится в миграциях;
- внешние сервисы подключаются через адаптеры;
- бизнес-логика не привязывается к одному облаку;
- конфигурация задаётся переменными окружения;
- пользовательские данные экспортируются в стандартном формате;
- резервное копирование проверяется регулярно.

---

# 19. Архитектурные запреты

Не допускается:

- прямой вызов TMDB из frontend с открытым токеном;
- хранение пользовательских данных внутри массива фильмов;
- зависимость UI от формата ответа внешнего API;
- смешивание каталога и пользовательских данных в одной сущности;
- хранение секретов в `index.html`;
- отправка персональных данных внешнему каталогу;
- привязка всех ID только к одному внешнему сервису;
- хранение единственной копии пользовательских данных без резервного копирования.

---

# 20. Приоритет MVP

Для MVP реализуем только необходимую основу:

1. собственная внутренняя модель фильма;
2. адаптер одного поставщика данных;
3. собственный API;
4. отдельная пользовательская модель;
5. хранение пользовательских данных в российском контуре;
6. возможность сменить поставщика без переделки интерфейса.

Не реализуем заранее:

- несколько региональных баз;
- сложную микросервисную архитектуру;
- автоматическую репликацию между странами;
- несколько каталогов одновременно;
- распределённую систему рекомендаций.

---

# 21. Основные архитектурные принципы

1. Каталог фильмов не содержит пользовательских данных.
2. Пользовательские данные не смешиваются с каталогом.
3. Внешние сервисы являются сменяемыми.
4. Приложение работает с собственной моделью фильма.
5. Frontend обращается только к нашему API.
6. Секреты не передаются в frontend.
7. Персональные данные российских пользователей хранятся в РФ.
8. Cloudflare и TMDB не являются обязательными частями архитектуры.
9. MVP остаётся простым, но не создаёт тупиков для дальнейшего развития.
10. Любое новое архитектурное решение сначала фиксируется в документации.

# 22. Текущая реализация общего каталога — 2026-08-07

- D1 binding: `MOVIES_DB`.
- Таблица: `movies`.
- `movie-details.js` реализует read-through cache: D1 → поставщик → D1.
- `catalog-search.js` читает только неперсональные данные из D1.
- Поиск не обращается к внешнему поставщику и не расходует его лимит.
- Добавление в «Хочу посмотреть» пока сохраняет личный статус только на устройстве.
- Следующий архитектурный этап — отдельные таблицы `users` и `user_library` с серверной авторизацией Telegram.


## 11. Навигационный контекст карточки

Полная карточка фильма должна знать экран-источник (`origin`): `home`, `library` или `catalog`.

Навигационное состояние, которое необходимо сохранять для корректного возврата:

- экран-источник;
- поисковый запрос;
- активные фильтры;
- выбранная вкладка «Моих фильмов»;
- позиция прокрутки списка.

Контекст возврата не должен храниться внутри данных фильма. Это состояние интерфейса/маршрутизации.

## 12. Модель «На вечер»

«На вечер» — не отдельный статус пользовательской кинотеки. Пользовательская связь использует:

- `status`: `none | watchlist | watched | rewatch`;
- `forTonight`: независимый boolean;
- `userRating`;
- `watchedDate`.

При `status = watched` значение `forTonight` должно сбрасываться в `false`.

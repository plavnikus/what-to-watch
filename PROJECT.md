# PROJECT.md

# Telegram Mini App «Что посмотреть?»

## Концепция

«Что посмотреть?» — личный помощник, который помогает быстро выбрать фильм или сериал из собственной кинотеки.

Это не каталог наподобие Кинопоиска. Главный критерий любого решения: помогает ли оно быстрее решить, что посмотреть сегодня.

## Цель MVP

Проверить основную гипотезу продукта: приложение заметно сокращает время и усилия на выбор фильма из уже интересующей пользователя кинотеки.

## Принципы продукта

- Один главный сценарий на экран.
- Большие зоны нажатия и мобильный UX.
- Минимум текста и действий до результата.
- Постепенное раскрытие информации.
- Каталог и пользовательские данные разделены архитектурно.
- MVP не перегружается функциями следующих версий.
- Архитектура должна масштабироваться без полной переделки.
- Ориентиры: Telegram, Apple Human Interface Guidelines, Netflix, IMDb, Letterboxd, Spotify.

## Реализовано

### Основные экраны

- Главная.
- «Мои фильмы».
- «Каталог».
- «Настройки».
- Полная карточка фильма.

### Личная кинотека

- Статусы «Хочу посмотреть» и «Просмотрено».
- Независимый флаг «На вечер».
- Личная оценка 1–10.
- Добавление и удаление фильмов.
- Фильтрация и поиск.
- Светлая, тёмная и системная темы.
- Серверная привязка личной кинотеки к подтверждённому Telegram-пользователю.

### Каталог

- Общий каталог хранится в Cloudflare D1 в таблице `movies`.
- Поиск выполняется через `/api/catalog-search`.
- Каталог начинается с поиска, а не с бесконечной ленты.
- До поиска доступны быстрые варианты выбора.
- Есть блок «Можно начать с этого» с компактной подборкой.
- Из каталога можно открыть карточку и добавить фильм в «Хочу посмотреть».

### Карточка фильма

Отображаются:

- баннер и постер;
- название и оригинальное название;
- год и тип;
- жанры;
- страна производства;
- длительность;
- описание;
- рейтинг Кинопоиска;
- рейтинг IMDb;
- личная оценка;
- пользовательские статусы;
- ссылки Кинопоиск / IMDb / Трейлер.

Страна уже хранится во внутренней модели данных. Это необходимо сохранить для будущих фильтров и естественных запросов вроде «американские комедии 90-х».

## Фильтры

Поддерживаются:

- тип;
- жанры;
- минимальный рейтинг Кинопоиска;
- год / диапазон лет.

В разделе «Мои фильмы» **нет скрытого минимального рейтинга по умолчанию**. Пользователь должен видеть всю свою кинотеку, пока сам явно не включит фильтр рейтинга.

Неизвестный внешний рейтинг хранится как `NULL`, а не как `0`.

## Контекстная навигация карточки

Карточка сохраняет экран-источник: Главная / Мои фильмы / Каталог.

- «Назад» возвращает на экран-источник.
- Для Каталога сохраняются поисковый запрос, фильтры и позиция списка.
- При прокрутке появляется закреплённая кнопка «Назад».
- Нижняя кнопка возврата имеет контекстную подпись.
- Нижняя навигация остаётся доступной; активным остаётся исходный раздел.

## Серверная архитектура MVP

Frontend опубликован через Cloudflare Pages.

Cloudflare D1 используется как серверное хранилище:

- `movies` — общий неперсональный каталог;
- `users` — пользователи;
- `user_movies` — пользовательская кинотека и личные статусы.

Рабочие Pages Functions:

- `/api/import-kinopoisk`;
- `/api/movie-details`;
- `/api/catalog-search`;
- `/api/user-library`;
- `/api/catalog-enrich` — служебное защищённое пакетное обогащение каталога;
- `/api/telegram-auth` — серверная проверка Telegram `initData` и создание/обновление Telegram-пользователя;
- `/api/telegram-session` — создание подписанной серверной сессии после проверки Telegram identity.

Временный `user-library-write-test.js` удалён и не является частью рабочего API. Временная диагностическая страница `telegram-auth-check.html` также удалена после успешной проверки. Одноразовый `/api/legacy-library-claim` удалён после успешного Production-перехода.

## Личная кинотека на сервере

Серверное хранение личной кинотеки реализовано и проверено.

Первичная миграция создала 1098 связей `user_movies` для `local_test_user`. На Telegram-этапе эти 1098 записей безопасно скопированы на подтверждённого владельца. Одноразовый серверный legacy-endpoint после проверки Production удалён. Исходные `local_test_user` записи пока сохранены как резерв; их удаление является отдельным решением и не входит в cleanup Telegram identity.

`/api/user-library` не использует `local_test_user` как текущего пользователя. Пользователь определяется по валидной подписанной Telegram session cookie.

Проверено в Production:

- Telegram Mini App открывается внутри Telegram через Production `telegram-entry.html`;
- `initData` успешно проверяется сервером;
- Telegram-пользователь создаётся/обновляется в `users`;
- без Telegram-сессии `/api/user-library` не выдаёт библиотеку;
- под основной Telegram identity доступны все 1098 перенесённых позиций;
- включение «На вечер» сохраняется после закрытия и повторного открытия Mini App;
- два разных Telegram-пользователя получают независимые кинотеки;
- изменение библиотеки второго пользователя не меняет библиотеку первого;
- один Telegram-пользователь видит одну и ту же библиотеку на другом устройстве;
- BotFather Menu Button настроен на Production `/telegram-entry.html`.

Сервер является основным источником состояния. `localStorage` используется как локальный cache/fallback и очередь повторной синхронизации при сетевых ошибках. При смене Telegram-пользователя локальные пользовательские данные очищаются, чтобы не смешивать библиотеки.

## Модель пользовательского состояния

```js
{
  status: "watchlist" | "watched" | "none",
  forTonight: boolean,
  userRating,
  watchedDate
}
```

`forTonight` — независимый флаг, а не отдельный статус.

При переводе фильма в `watched` флаг `forTonight` должен сбрасываться.

## Данные каталога

После миграции в `movies` присутствуют записи для 1098 фильмов пользовательской кинотеки.

Историческая контрольная точка после queue-safe пакетного обогащения: 294 карточки были полноценно обогащены через ПоискКино API, 804 записи оставались в состоянии `library_migration`. После включения ежедневной автоматики очередь продолжает уменьшаться, поэтому эту цифру не считать текущим живым остатком.

Минимальные записи `source='library_migration'` и `source='library_migration_failed'` не считаются полноценным cache hit. При первом открытии такой карточки `/api/movie-details` пытается получить полные метаданные у внешнего поставщика и сохранить их в D1. Если поставщик временно недоступен, пользователь всё равно получает имеющуюся минимальную запись.

Для контролируемого фонового наполнения используется `/api/catalog-enrich`. Он:

- выбирает только `source='library_migration'`;
- не тратит запросы на уже обогащённые записи;
- работает порциями до 25 фильмов за запуск;
- защищён секретом `CATALOG_ENRICH_KEY`;
- использует `POISKKINO_API_TOKEN` только на сервере;
- при временной ошибке переносит запись в конец очереди, чтобы один фильм не блокировал остальные;
- при явной ошибке конкретного фильма (`404/410/422`) переводит его в `library_migration_failed`, исключая из фоновых партий;
- `library_migration_failed` всё равно повторно проверяется при ручном открытии карточки.

Queue-safe успешный сценарий проверен на Preview: `requested=1`, `attempted=1`, `enriched=1`, `failed=0`, `stopped=false`.

Ежедневное фоновое обогащение работает через GitHub Actions workflow `.github/workflows/catalog-enrichment.yml`:

- запуск один раз в сутки;
- максимум 6 партий по 25 фильмов — до 150 попыток обогащения за scheduled-run;
- ручной `workflow_dispatch` безопасен по умолчанию: 1 партия × 1 фильм;
- при пустой очереди workflow завершает работу досрочно;
- при глобальной ошибке поставщика (`401/402/403/429`) дальнейшие партии не запускаются;
- транспортный таймаут `curl` с кодом 28 фиксируется и не роняет весь scheduled-run: workflow переходит к следующей партии;
- другие транспортные ошибки и HTTP non-200 по-прежнему считаются ошибкой job;
- доступ к Production endpoint выполняется через GitHub repository secret `CATALOG_ENRICH_KEY`, сам секрет в репозиторий не записывается;
- Production `CATALOG_ENRICH_KEY` и GitHub repository secret синхронизированы;
- ручной Production-тест workflow успешно выполнен: `attempted=1`, `enriched=1`, `failed=0`;
- первый самостоятельный scheduled-run успешно выполнен в Production: `attempted=150`, `enriched=150`, `failed=0`;
- scheduled-run #9 успел обогатить ещё 24 карточки перед транспортным таймаутом второй партии; последняя подтверждённая контрольная точка очереди после этой партии — `pendingAfter=328`.

GitHub Actions schedule может стартовать позже указанной cron-минуты; для этой фоновой задачи критична ежедневная регулярность, а не точное время запуска.

Отсутствие постера или рейтинга не означает отсутствие фильма.

Ошибочные значения `rating_kp = 0`, появившиеся при миграции для неизвестных рейтингов, были исправлены на `NULL`.

Тестовые seed-фильмы не должны смешиваться с реальной пользовательской кинотекой.

После завершения фоновой очереди нужен финальный аудит каталога: проверить остаток `library_migration`, количество `library_migration_failed`, полноту ключевых полей и сохранность пользовательских связей `user_movies`. Этот аудит выполняется параллельно и не блокирует Telegram-разработку.

## Telegram Mini App — текущий этап

Telegram identity, серверная сессия и разделение личных библиотек реализованы и проверены в Production.

Архитектура:

- `telegram-entry.html` получает `Telegram.WebApp.initData`;
- backend проверяет подпись и `auth_date` с `TELEGRAM_BOT_TOKEN`;
- создаёт/обновляет пользователя в `users`;
- создаёт подписанную `HttpOnly; Secure; SameSite=Lax` session cookie;
- `/api/user-library` использует только подтверждённый `userId` из этой сессии;
- общий каталог `movies` остаётся единым для всех;
- личные состояния остаются в `user_movies`.

Одноразовый перенос старой библиотеки завершён. Серверный `/api/legacy-library-claim` больше не является частью рабочей архитектуры. Резервные записи `local_test_user` пока сохранены и не участвуют в определении текущего пользователя.

Проверено:

- Telegram identity;
- разделение от `local_test_user`;
- перенос 1098 позиций владельцу;
- запись и повторное чтение «На вечер»;
- независимость библиотек двух разных Telegram-пользователей;
- одна библиотека одного Telegram-пользователя на разных устройствах;
- Production deployment и Production Menu Button.

Frontend пока сохраняет совместимый маркер завершённой старой localStorage → server миграции, потому что текущий `index.html` использует его также для синхронизации новых импортированных фильмов. Удалять этот маркер нужно отдельной правкой после отвязки от активного сценария импорта.

## Импорт

Импорт публичного списка Кинопоиска работает через Pages Functions.

Внешний источник метаданных вызывается через серверный адаптер. Карточка сначала читается из D1; внешний API вызывается только когда данные нужно получить или обогатить.

## Не входит в текущий MVP

- групповой выбор;
- Tinder/турнир;
- AI-подбор;
- сложные коллекции;
- расширенная статистика.

Эти функции остаются в Roadmap и не должны замедлять проверку основной гипотезы.
